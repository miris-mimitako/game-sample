# ドラクエ風ターン制バトル アプリケーション設計書

## 1. 目的

本設計書では、ドラクエ風ターン制バトルをC#で実装するためのアプリケーション全体構造を定義する。

以下を基本方針とする。

- C#を使用する
- Domain Driven Designを採用する
- Bounded Contextを分離する
- データベースは使用しない
- 初期データは外部ファイルから読み込む
- ドメイン層をファイル形式に依存させない
- 戦闘中の状態はメモリ上で管理する

## 2. 全体アーキテクチャ

アプリケーションを大きく以下に分離する。

```text
Presentation
     ↓
Application
     ↓
Domain

Infrastructure
     ↑
Application
```

依存関係の中心はDomainとする。

DomainからApplication、Infrastructure、Presentationを参照してはならない。

## 3. Bounded Context

現時点では、以下の2つのBounded Contextに分離する。

```text
Battle Context

Battle Setup Context
```

戦闘そのものをCore Domainとする。

Battle Setupは、戦闘開始に必要となる外部データを準備するSupporting Domainとして扱う。

## 4. Battle Context

Battle Contextはゲームの戦闘ルールを担当する。

本システムのCore Domainとする。

Battle Contextには以下の概念を配置する。

```text
Battle
BattleParticipant
Turn
Equipment
Attack
Magic
StatusEffect
Death
BattleResult
```

ここには、

```text
JSON
ファイルパス
ファイル読み込み
画面表示
Console
```

などの外部技術を持ち込まない。

## 5. Battle Setup Context

Battle Setup Contextは、戦闘開始に必要となるデータを外部から取得し、Battle Contextが利用可能な入力へ変換する。

主な責務は、

```text
外部ファイルの読み込み
入力形式の検証
戦闘開始データへの変換
Battle Contextへの受け渡し
```

とする。

Battle Setup Contextは戦闘ルールを持たない。

例えば、

```text
HPが0なら死亡
攻撃力 / 2 - 守備力 / 4
毒は10ダメージ
```

といったルールはBattle Contextだけが知る。

## 6. Context間の関係

Battle Setup ContextからBattle Contextへ、ファイルオブジェクトを直接渡さない。

以下のような流れとする。

```text
battle.json
    ↓
Battle Setup Context
    ↓
File DTO
    ↓
Validation / Translation
    ↓
Battle開始要求
    ↓
Battle Context
    ↓
Battle生成
```

Battle Contextは、

```text
どのファイルから読み込まれたか
JSONだったか
CSVだったか
```

を知らない。

## 7. Battle ContextのAggregate

Battle Contextの中心となるAggregate Rootを`Battle`とする。

概念構造は以下とする。

```text
Battle
 ├─ PlayerTeam
 │    ├─ BattleParticipant
 │    └─ BattleParticipant
 │
 ├─ EnemyTeam
 │    ├─ BattleParticipant
 │    └─ BattleParticipant
 │
 ├─ CurrentTurn
 └─ BattleResult
```

Battleは戦闘全体の整合性を管理する。

## 8. Battleの責務

Battleは以下を担当する。

```text
主人公側参加者の管理
敵側参加者の管理

戦闘開始

Turn生成

戦闘継続判定

全滅判定

勝利判定

敗北判定

次ターンへの移行
```

個別のダメージ計算などはBattle自身では行わない。

## 9. BattleParticipant

BattleParticipantは、今回の戦闘に参加しているキャラクターを表すEntityとする。

Entityとして識別情報を持つ。

概念上、以下を保持する。

```text
BattleParticipant
 ├─ ParticipantId
 ├─ Name
 ├─ Team
 ├─ HP
 ├─ MP
 ├─ BaseStatus
 ├─ Equipment
 └─ StatusEffects
```

BattleParticipantはCharacterそのものではなく、

```text
今回の戦闘に参加しているキャラクター
```

を表現する。

## 10. BattleParticipantの責務

BattleParticipant自身が以下の整合性を保証する。

```text
HPを0未満にしない

HPを最大HPより大きくしない

MPを0未満にしない

死亡状態をHPから判定する

ダメージを受ける

HPを回復する

MPを消費する

装備補正を反映した能力値を提供する

状態異常を保持する
```

外部から直接HPを書き換えることは許可しない。

例えば、

```csharp
participant.CurrentHp = 0;
```

とはしない。

概念的には、

```csharp
participant.TakeDamage(damage);
```

を通して状態を変化させる。

## 11. Equipment

EquipmentはValue Objectとする。

IDを持たない。

以下の値によって同値判定する。

```text
Name
EquipmentType
MaxHpModifier
MaxMpModifier
AttackModifier
DefenseModifier
AgilityModifier
```

すべて一致する場合のみ同値とする。

EquipmentはImmutableとする。

## 12. Turn

TurnはBattle内部でのみ意味を持つドメインオブジェクトとする。

Battleとは独立したAggregate Rootにはしない。

概念上、

```text
Battle
 └─ Turn
```

というライフサイクルとする。

Turnは、

```text
TurnNumber
参加者
選択行動
行動順
行動済み状態
終了理由
```

を管理する。

## 13. Turnの責務

Turnは、

```text
誰が
このターンに
何を選択して
どの順番で
行動済みになったか
```

を管理する。

BattleParticipant自身には、

```text
ActionConsumed
```

を持たせない。

行動済みかどうかは、

```text
BattleParticipantの状態
```

ではなく、

```text
BattleParticipantとTurnとの関係
```

だからである。

## 14. Action

行動には以下を定義する。

```text
Attack
Defense
Magic
Escape
Item
```

行動選択結果は、

```text
SelectedAction
```

として表現する。

概念上、

```text
SelectedAction
 ├─ ActorId
 ├─ ActionType
 └─ TargetId
```

とする。

対象が不要な行動ではTargetIdを持たない。

## 15. Attack

Attackは通常攻撃のドメインルールを担当する。

主な責務は、

```text
命中判定
会心判定
物理ダメージ計算
防御状態の考慮
AttackResult生成
```

とする。

Attackは、

```text
Turnを進める
Battleを終了する
```

ことはしない。

## 16. Magic

Magicは魔法そのものを表現するValue Objectとする。

現時点では、

```text
Mera
Hoimi
```

を扱う。

MagicActionは、

```text
どの魔法を
誰に使うか
```

を表現する。

```text
Magic
```

と、

```text
MagicAction
```

は分離する。

## 17. StatusEffect

状態異常として以下を扱う。

```text
Poison
Paralysis
```

状態異常はBattleParticipantが保持する。

Poisonはターン終了時に評価する。

Paralysisは行動時に評価する。

Turn自身は、

```text
毒は10ダメージ
麻痺は3回
```

というルールを持たない。

## 18. Death

死亡専用EntityやValue Objectは作成しない。

```text
CurrentHp = 0
```

を死亡の唯一の事実とする。

概念上、

```csharp
participant.IsDead
```

はCurrentHpから導出する。

## 19. Application Layer

Application Layerはユースケースを実現する。

ドメインルールそのものは記述しない。

Application Layerの役割は、

```text
入力を受け取る
必要なDomain Objectを取得する
Domain Objectへ処理を依頼する
結果をPresentationへ返す
```

こととする。

## 20. Application Use Case

現時点では以下のUse Caseを用意する。

```text
LoadBattleScenario

StartBattle

SelectAction

ExecuteTurn

GetBattleState
```

## 21. LoadBattleScenario

外部ファイルから戦闘開始用データを読み込むUse Caseとする。

処理の流れは、

```text
ファイル指定
↓
ScenarioReader
↓
入力DTO
↓
Validation
↓
Battle開始用データ
```

とする。

戦闘そのものはまだ開始しない。

## 22. StartBattle

読み込み済みのBattle開始データからBattle Aggregateを生成する。

概念上、

```text
BattleStartData
↓
BattleFactory
↓
Battle
```

とする。

参加人数、

```text
主人公 1～4
敵     1～4
```

などのドメインルールについてはDomain側で保証する。

## 23. SelectAction

ユーザーが選択した行動を現在Turnへ登録する。

例えば、

```text
勇者
Attack
Target = SlimeA
```

をApplication Layerが受け取り、

```text
Battle
↓
CurrentTurn
↓
SelectAction
```

へ委譲する。

Application Layer自身では、

```text
攻撃可能か
死亡しているか
```

などを独自判定しない。

## 24. ExecuteTurn

必要な行動がすべて登録された後、現在Turnを実行する。

概念的には、

```text
ExecuteTurn
↓
Battle.ExecuteCurrentTurn()
↓
Domain処理
↓
TurnResult
```

とする。

実行中には、

```text
攻撃
魔法
麻痺
死亡
毒
戦闘終了
```

などのドメイン処理が発生する。

## 25. GetBattleState

Presentationが現在の戦闘状態を表示するために使用する。

Domain Entityを直接Presentationへ渡さない。

Application用の出力モデルへ変換する。

概念上、

```text
Battle
↓
BattleStateDto
↓
Presentation
```

とする。

## 26. Infrastructure Layer

Infrastructure Layerは外部技術との接続を担当する。

今回の主な役割はファイルアクセスと乱数生成とする。

```text
Infrastructure
 ├─ File
 └─ Random
```

## 27. ファイル読み込み

Application側には抽象を定義する。

概念上、

```csharp
public interface IBattleScenarioReader
{
    BattleScenarioData Read(string path);
}
```

Infrastructure側で具体的な読み込み方法を実装する。

例えばJSONを採用する場合、

```text
IBattleScenarioReader
          ↑
JsonBattleScenarioReader
```

とする。

## 28. ファイル形式への依存

JSONを利用する場合でも、

```csharp
JsonSerializer
JsonPropertyName
JsonElement
```

などをDomain Layerへ持ち込まない。

JSON専用DTOをInfrastructure Layerに配置する。

概念上、

```text
battle.json

↓ Deserialize

BattleScenarioFileDto

↓ Mapping

BattleStartData

↓ Domain

Battle
```

とする。

## 29. ファイルDTO

外部ファイル構造を表すDTOを用意する。

概念上、

```text
BattleScenarioFileDto
 ├─ Players[]
 └─ Enemies[]
```

参加者は、

```text
ParticipantFileDto
 ├─ Name
 ├─ Hp
 ├─ Mp
 ├─ Attack
 ├─ Defense
 ├─ Agility
 ├─ Weapon
 ├─ Armor
 └─ Accessory
```

などを保持する。

DTOはDomain Objectではない。

## 30. ファイルDTOとDomainの分離

例えばファイルに、

```json
{
  "name": "勇者",
  "hp": 100,
  "attack": 30
}
```

と書かれていても、

```text
ParticipantFileDto
```

をそのままBattleParticipantとして使用しない。

必ず、

```text
File DTO
↓
変換
↓
Domain Object
```

を行う。

これによりファイル仕様変更がDomainへ直接波及することを防ぐ。

## 31. BattleFactory

Battle生成処理が複雑になるため、BattleFactoryをDomain側に配置できるものとする。

概念上、

```csharp
BattleFactory.Create(BattleStartData)
```

とする。

BattleFactoryは、

```text
BattleParticipant生成
Team構築
人数確認
初期Turn準備
```

などBattle生成時の整合性を保証する。

## 32. Repository

現時点ではRepositoryを導入しない。

理由は、Battle Aggregateをデータベースや永続ストレージへ保存する要件が存在しないためである。

ファイルは、

```text
Battle Aggregateの保存先
```

ではなく、

```text
Battleを作るための入力元
```

として扱う。

したがって、

```text
BattleRepository
EquipmentRepository
ParticipantRepository
```

などは作成しない。

## 33. 戦闘状態の保持

戦闘中のBattle Aggregateはメモリ上に保持する。

アプリケーションが1つの戦闘だけを実行する場合、

```text
BattleApplicationService
 └─ CurrentBattle
```

という形で管理可能とする。

複数戦闘を並列管理する要件が発生するまでは、

```text
IBattleRepository
IBattleSessionStore
```

などを導入しない。

## 34. Random

すばやさ同値判定、攻撃ミス、会心などで乱数を使用する。

Domainロジックから.NETの乱数生成を直接呼び出さない。

概念上、

```csharp
public interface IRandomSource
{
    double NextDouble();
    ulong NextUInt64();
}
```

を利用する。

具体実装はInfrastructureへ配置する。

```text
Domain/Application
       ↓
IRandomSource
       ↑
SystemRandomSource
```

とする。

テストでは固定値を返すFakeを利用する。

## 35. Presentation Layer

Presentation Layerはユーザーとの入出力だけを担当する。

最初の実装はConsole Applicationでもよい。

Presentationは、

```text
現在HP表示
行動選択
対象選択
結果表示
```

を担当する。

戦闘ルールをPresentationへ記述しない。

例えば、

```csharp
if (target.Hp == 0)
{
    // 死亡
}
```

のような判定をPresentation側で行わない。

Domainが提供する結果を表示するだけとする。

```text

```

永続化要件がないためPersistenceフォルダは作成しない。

## 40. BattleSetup.Application

ファイルから戦闘データを取得するユースケースを定義する。

```text

  Abstractions/
    IBattleScenarioReader.cs
```

## 41. BattleSetup.Infrastructure

具体的なファイル読み込みを配置する。

JSONを利用する場合、

```text
BattleSetup.Infrastructure/

  Json/
    JsonBattleScenarioReader.cs

    Dtos/
      BattleScenarioFileDto.cs

      BattleScenarioMapper.cs
```

とする。

## 42. プロジェクト依存関係

依存関係は以下とする。

```text
Battle.Domain
    ↑
Battle.Application
    ↑
Presentation
```

Infrastructureは抽象を実装する。

```text
Battle.Application
    ↑
Battle.Infrastructure
```

Battle Setupについても同様とする。

```text
BattleSetup.Application
       ↑
BattleSetup.Infrastructure
```

BattleSetupからBattleへ渡す際には、明確な変換境界を設ける。

## 43. Shared Kernel

最初から大きなShared Kernelを作らない。

Battle ContextとBattle Setup Contextで必要な型が似ていても、安易に共通化しない。

例えば、

```text
BattleParticipant
ParticipantFileDto
```

は別の型とする。

名前や項目が似ていても責務が異なるためである。

共通化が明確に必要になった場合のみShared Kernelを検討する。

## 44. DomainとDTOの違い

DTOは外部データを運ぶための構造とする。

Domain Objectはゲームルールを守るための構造とする。

例えばDTOでは、

```text
Hp = -100
```

というデータを一時的に保持する可能性がある。

しかしBattleParticipantは、

```text
HP >= 0
```

という不変条件を必ず守る。

そのため、

```text
DTO生成成功
=
Domain生成成功
```

とは限らない。

## 45. エラー処理

エラーを大きく以下に分類する。

### 外部入力エラー

例えば、

```text
ファイルが存在しない
JSON形式が壊れている
必須項目がない
```

など。

Battle Setup / Infrastructure側で扱う。

### ドメインルール違反

例えば、

```text
主人公が0人
敵が5人
HPが不正
最大MPが999を超える
```

など。

Domain側で拒否する。

### 行動失敗

例えば、

```text
MP不足
対象死亡
麻痺
```

など。

これはシステムエラーではない。

正常なゲーム上の結果として扱う。

## 50. 結論

本アプリケーションでは、

```text
Battle Context
```

をCore Domainとする。

ファイルからデータを読み込む処理は、

```text
Battle Setup Context
```

へ分離する。

Battle Context内部では、

```text
Battle
```

をAggregate Rootとし、

```text
BattleParticipant
Turn
Equipment
Attack
Magic
StatusEffect
```

などのドメインモデルによって戦闘ルールを表現する。

データベースを使用しないため、Repository Patternは現時点では導入しない。
